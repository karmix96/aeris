COMMON FOLDER — FOUNDATION LAYER
================================

Purpose
-------
Infrastructure backbone of AERIS.

This layer handles:
- config loading
- path resolution
- data/output directory conventions
- run folder creation
- logging setup

It must stay domain-neutral.

It must NOT contain:
- BWB geometry logic
- AVL / CFD solver logic
- ML training logic
- QC policy logic
- dynamics / trim logic


Key modules
-----------

config.py
    load_yaml_config()
    file_sha256()

    Loads YAML safely with minimal structural validation.
    Computes config/file hashes for future reproducibility manifests.
    Does not perform domain-specific schema validation.

logging_utils.py
    setup_logger()
    make_process_log_file()
    log_and_echo()

    Creates rotating file logger plus optional console logger.
    Closes old handlers correctly.
    Avoids default logger-name collisions by deriving names from log paths.
    Supports text logs and JSON-lines logs.

paths.py
    PROJECT_ROOT
    CONFIGS_DIR
    DATA_DIR
    RUNS_DIR
    DATASETS_DIR
    create_run_folder()
    describe_path_environment()

    Resolves project/config/data directories.
    Supports editable installs, packaged installs, Windows/Linux machines,
    cluster scratch, and cloud-style output directories.


Environment variables
---------------------

AERIS_PROJECT_ROOT
    Optional project/source/workspace root.

AERIS_CONFIGS_DIR or AERIS_CONFIG_ROOT
    Optional explicit configs directory.

AERIS_DATA_DIR or AERIS_DATA_ROOT
    Optional explicit generated-data/output directory.

AERIS_USE_CLUSTER_SCRATCH
    If true and no explicit data dir is set, prefer SLURM_TMPDIR, SCRATCH,
    or TMPDIR for generated output.


Recommended cluster example
---------------------------

export AERIS_PROJECT_ROOT="$PWD"
export AERIS_CONFIGS_DIR="$PWD/configs"
export AERIS_DATA_DIR="$SCRATCH/aeris_data"


Production principles
---------------------

1. Source code location is not output location.
2. Generated data should be redirectable.
3. Every run gets its own folder.
4. Run folders are timestamped and collision-resistant.
5. Logging should be persistent, rotating, and optionally quiet.
6. Parallel workers should not write to the same log file.
7. Common utilities should be boring, stable, and domain-neutral.

Cluster / Cloud Usage Notes
---------------------------

Core rule:
    Never assume the installed Python package location is writable.

On a cluster or cloud worker, AERIS should treat these as separate locations:

    1. Code location
        Where the AERIS package is installed.
        This may be read-only, e.g. site-packages, /opt/aeris, or a container image.

    2. Project/config location
        Where configs live.
        Usually the checked-out project folder or a mounted config directory.

    3. Data/output location
        Where generated runs, datasets, logs, and artifacts are written.
        Usually scratch storage, a mounted volume, or cloud-backed storage.

Recommended cluster setup:

    cd /path/to/aeris/project

    export AERIS_PROJECT_ROOT="$PWD"
    export AERIS_CONFIGS_DIR="$PWD/configs"
    export AERIS_DATA_DIR="$SCRATCH/aeris_data"

    python -m pip install -e .
    aeris --help

Alternative packaged-install setup:

    python -m pip install aeris.whl

    export AERIS_PROJECT_ROOT="/path/to/workspace"
    export AERIS_CONFIGS_DIR="/path/to/workspace/configs"
    export AERIS_DATA_DIR="$SCRATCH/aeris_data"

    aeris --help

Cloud/container setup:

    export AERIS_PROJECT_ROOT="/workspace"
    export AERIS_CONFIGS_DIR="/workspace/configs"
    export AERIS_DATA_DIR="/mnt/aeris_data"

    aeris --help

Do not write heavy outputs to:

    - site-packages
    - read-only container layers
    - cluster home directories with small quotas
    - shared network folders unless intentionally configured

Parallel execution rule:

    Each worker/process must write to its own case/run folder or its own log file.
    Multiple workers must not append directly to the same CSV or write to the same
    solver working directory.

Correct parallel pattern:

    main process:
        creates dataset/run root
        creates task list with deterministic IDs
        dispatches tasks

    worker process:
        writes isolated artifacts to its own case folder
        writes its own log file
        returns status/result fragment

    main process:
        collects fragments
        writes final metadata.csv
        writes final failures.csv
        writes final manifest.json

Wrong parallel pattern:

    many workers appending to metadata.csv at the same time
    many workers writing to one app.log
    many solver cases sharing one temporary output directory

For SLURM/cloud integration later, build an execution layer instead of putting
cluster-specific logic inside geometry/aero/dataset modules.
