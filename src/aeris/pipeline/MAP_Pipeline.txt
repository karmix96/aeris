AERIS PIPELINE — OVERVIEW
========================

Folder:
src/aeris/pipeline/

Files:
- geometry_run.py
- smoke.py

Purpose:
--------
The pipeline layer is the orchestration layer of AERIS.

It connects:
CLI → framework → generators → artifacts

It is NOT:
- business logic
- geometry logic
- aero logic

It IS:
- execution coordinator
- reproducibility enforcer
- manifest/logger manager

Think of it as:
“the production line controller of the factory”


--------------------------------------------------
CORE RESPONSIBILITIES
--------------------------------------------------

1) Load config
2) Create run folder (reproducibility)
3) Setup logging
4) Resolve generator (via registry)
5) Sample design (controlled randomness)
6) Run deterministic generation
7) Store artifacts
8) Write manifest (traceability)
9) Handle failures cleanly


--------------------------------------------------
FILES BREAKDOWN
--------------------------------------------------

1) geometry_run.py
------------------

Main production pipeline for geometry generation.

ENTRYPOINT:
run_geometry_generation(config_path)

FLOW:
------
config_path
  ↓
load_yaml_config()
  ↓
create_run_folder()
  ↓
setup_logger()
  ↓
resolve_generator_and_config()
  ↓
get_geometry_generator()
  ↓
generator.sample_one()
  ↓
generator.run_full_case()
  ↓
generator.summarize_case()
  ↓
write manifest.json

IMPORTANT CONCEPT:
------------------
Sampling = stochastic (seeded)
Geometry = deterministic

This separation is CRITICAL.


HELPER FUNCTIONS:
----------------
- _utc_now_iso()
  → timestamp generation

- _to_jsonable()
  → converts dataclasses, numpy, Path → JSON-safe

- _write_manifest()
  → writes manifest.json

- _mark_manifest_failed()
  → standardized failure structure


OUTPUT:
-------
Run folder:
data/runs/<run_id>/

Contains:
- input_config.yaml
- logs/app.log
- artifacts/geometry/*
- manifest.json


MANIFEST STRUCTURE:
-------------------
{
  run_id
  phase
  status
  timestamps
  platform
  python_version
  geometry: {
    generator info
    sample
    summary
  }
}


--------------------------------------------------

2) smoke.py
-----------

Minimal validation pipeline.

Purpose:
--------
Quick sanity check of full system without full dataset or heavy runs.

FLOW:
------
Same as geometry_run BUT:
- simpler manifest
- minimal outputs
- no extended metadata
- used for testing/debugging


ENTRYPOINT:
run_smoke_pipeline(config_path)


KEY DIFFERENCE FROM geometry_run:
--------------------------------
geometry_run → production-grade
smoke        → lightweight validation


--------------------------------------------------
IMPORTANT DESIGN PATTERNS
--------------------------------------------------

1) PIPELINE ≠ LOGIC

Pipeline never:
- computes geometry
- defines sampling rules
- performs validation logic

It delegates EVERYTHING.


2) REGISTRY-BASED RESOLUTION

No hardcoded generators.

generator_id → registry → implementation


3) REPRODUCIBILITY FIRST

Every run:
- has unique run_id
- stores input config
- logs everything
- produces manifest


4) MANIFEST AS SOURCE OF TRUTH

Everything important is written to manifest.json:
- inputs
- outputs
- errors
- metadata

This is future ML / audit backbone.
