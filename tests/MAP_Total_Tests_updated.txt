AERIS MAP — TOTAL TESTS, TEST INTENT, GAPS, AND PRODUCTION PREFLIGHT
Checkpoint: Geometry + Aero + QC + Retention + Curation + E2E Smoke

==================================================
0. PURPOSE OF THIS DOCUMENT
==================================================

This file explains:

1. What each test area is trying to prove
2. What those tests do NOT prove
3. How to use the test suite in practice
4. What to run before:
   - local development
   - a light personal E2E run
   - a medium validation campaign
   - a large production/cloud campaign

Important distinction:

- Runtime workflow uses the real application code.
- Pytest tests do NOT run during production workflows.
- Pytest tests only verify beforehand that the real code behaves as expected.

So:

QC in the workflow:
- uses the QC implementation functions directly

Pytest:
- checks those functions and the surrounding plumbing

==================================================
2. HOW TO THINK ABOUT THE TEST SUITE
==================================================

The test suite has four roles.

A. UNIT / COMPONENT TESTS
They test one function, helper, validator, model, parser, exporter, or adapter in isolation.

Purpose:
- catch local regressions fast
- verify small logic pieces
- make refactoring safer

B. INTEGRATION TESTS
They test a few layers working together.

Examples:
- CLI -> command -> pipeline
- dataset -> QC
- aero manifest ordering -> integrated QC
- geometry export -> replay/read path

Purpose:
- verify plumbing between modules
- catch interface drift

C. E2E / WORKFLOW SMOKE TESTS
They run a real small workflow and inspect the outputs.

Purpose:
- prove the chain still hangs together
- catch breakage that unit tests miss

D. MANUAL / OPERATIONAL RUNS
These are not pytest tests.
These are real runs executed by the user or by production infrastructure.

Purpose:
- prove the system survives scale, duration, solver weirdness, and storage pressure

==================================================
4. WHAT THE RUNTIME WORKFLOW USES
==================================================

When you run:

aeris dataset aero-generate ...

the runtime workflow uses:
- real geometry generation code
- real aero sweep code
- real QC runner functions
- real manifest and summary writers
- real retention logic
- real curation only if you run it afterwards

It does NOT use:
- pytest files
- test helpers except indirectly through confidence they provide

So:

Workflow QC:
- uses QC implementation code directly

Pytest:
- proves that implementation is behaving as expected

6. WHAT IS MISSING OR SHOULD STILL BE ADDED
==================================================

Recommended future additions:

1. Medium-scale operational rehearsal script/check
- not necessarily a pytest
- something like 20–50 geometries with real campaign settings
- used before true production launches

2. Resume / restart behavior tests
- currently missing
- important for long runs

3. Failure-chain integration tests
Examples:
- solver partial failure -> manifest -> QC -> curation -> retention
- geometry partial corruption -> inspect -> QC -> curate rejection

4. Empty-file / empty-dataset robustness tests
Especially around:
- empty aero_failures.csv
- zero-row curated outputs
- partial artifact deletion

5. Cloud/HPC environment tests
Eventually:
- filesystem semantics
- job timeouts
- worker interruption
- storage cleanup expectations

6. Production naming and collision behavior tests
- repeated dataset name behavior under production usage
- archive/cleanup workflow tests

7. Optional golden-reference tests
- selected fixed geometry / fixed aero outputs
- used cautiously to catch silent drift

==================================================
7. STANDARD PREFLIGHT CHECKLIST
==================================================

--------------------------------------------------
7.1 CASE A — DAY-TO-DAY LOCAL DEVELOPMENT
--------------------------------------------------

Use when:
- editing one module
- refactoring helpers
- changing one command
- changing one validator
- changing one generator feature

Run:
1. the nearest unit/component tests first
2. then the directly related integration tests
3. do not run the whole universe unless the change is broad

Examples:
- if changing quality logic:
  pytest tests/quality tests/dataset/test_aero_qc_integration.py -v

- if changing dataset CLI:
  pytest tests/commands/test_dataset.py tests/dataset -v

- if changing generator internals:
  pytest tests/generators/bwb_segmented_v1 tests/pipeline/test_geometry_run.py -v

Goal:
Fast feedback, focused failures, no wasted time.

--------------------------------------------------
7.2 CASE B — LIGHT PERSONAL E2E RUN
--------------------------------------------------

Use when:
- you want to personally sanity-check the system
- you changed workflow wiring
- you want quick confidence before a small run

Run this test gate:
pytest tests/quality tests/dataset tests/commands tests/e2e -v

Then run one tiny real command:
- geometry-only: n=1 to 3
- aero: n=1 to 2, tiny sweep

Then manually inspect:
- manifest
- final_run_summary.json
- QC reports
- retention result
- curated outputs if relevant

Goal:
Prove the whole chain still works in practice.

--------------------------------------------------
7.3 CASE C — MEDIUM VALIDATION CAMPAIGN
--------------------------------------------------

Use when:
- you changed important workflow behavior
- you changed solver/plumbing/QC/retention/curation
- you are preparing for production

Run this gate:
pytest tests/common tests/quality tests/dataset tests/aero tests/commands tests/e2e -v

Then launch a medium rehearsal:
- 10 to 50 geometries
- real solver
- real QC preset
- intended retention mode
- realistic sweep settings

After run, inspect:
- failure rate
- summary consistency
- QC pass/fail
- disk usage
- kept/deleted aero run roots
- curated kept vs rejected counts

Goal:
Catch operational issues that smoke tests will not reveal.

--------------------------------------------------
7.4 CASE D — LARGE LOCAL OR WORKSTATION PRODUCTION RUN
--------------------------------------------------

Use when:
- you want a long unattended run on your machine/server

Before launch:
1. working tree clean or committed
2. exact command saved
3. unique dataset name chosen
4. preflight tests passed
5. medium rehearsal already passed for similar setup
6. disk budget checked
7. retention mode intentionally chosen
8. solver executable confirmed
9. config file frozen for the campaign

Recommended preflight gate:
pytest tests/quality tests/dataset tests/aero tests/commands tests/e2e -v

Launch recommendations:
- use --qc-preset production
- use retain_aero_runs=failures_only unless there is a good reason not to
- choose whether to keep intermediate geometry dataset intentionally
- archive final summary and manifest immediately after completion

Post-run:
- inspect final_run_summary.json first
- inspect manifest second
- inspect QC reports third
- run curate-aero for ML acceptance if needed

Goal:
Controlled production, not improvisation.

--------------------------------------------------
7.5 CASE E — CLOUD / PRODUCTION-LEVEL RUN
--------------------------------------------------

Use when:
- running in cloud, HPC, remote worker, or scheduled production environment

Suggested process:

Stage 0 — Code gate
- run regression suite in CI or equivalent:
  pytest tests/quality tests/dataset tests/aero tests/commands tests/e2e -v

Stage 1 — Environment preflight
- confirm solver installed and callable
- confirm filesystem layout and write permissions
- confirm job time/memory/disk budget
- confirm dataset naming convention
- confirm cleanup/archive policy

Stage 2 — Small environment shakeout run
- run a tiny real campaign in the target environment
- confirm manifests, summary, QC, retention, and artifact paths look correct

Stage 3 — Medium environment rehearsal
- run a realistic but smaller-than-production campaign
- observe failure rate and storage behavior

Stage 4 — Production campaign
- launch with locked config and documented command
- monitor logs and summary artifacts
- preserve final summary, manifest, QC, and curated outputs

Stage 5 — Acceptance
- inspect final summary
- inspect QC results
- run curation
- archive approved outputs
- delete transient artifacts according to policy

Important:
Cloud production should not depend on “I ran some unit tests locally and vibes looked good.”

==================================================
8. WHAT YOU SHOULD NOT DO
==================================================

Do NOT:
- run every single test before every tiny edit
- assume passing unit tests means large campaigns are safe
- assume E2E smoke means operational proof
- ignore disk/retention planning
- launch a week-long campaign without a medium rehearsal
- confuse pytest files with runtime QC behavior

==================================================
9. RECOMMENDED DEFAULT TEST GATES
==================================================

Fast focused gate:
pytest tests/quality tests/dataset tests/commands -v

Strong local gate:
pytest tests/quality tests/dataset tests/aero tests/commands tests/e2e -v

Broad regression gate:
pytest -v

Use pytest -v when:
- broad cross-domain changes happened
- before important branch merges
- before major release/checkpoint milestones

10. FINAL HONEST SUMMARY
==================================================

AERIS now has a serious and useful test structure.

It is strong in:
- geometry
- dataset generation
- QC
- command wiring
- summary/retention/curation plumbing
- small real workflow validation

It is not yet fully proven in:
- large production operations
- resumability
- cloud/HPC robustness
- long-duration failure behavior

So the right engineering statement is:

“AERIS is test-backed and workflow-validated at small scale, with medium/large operational validation still required before claiming production maturity.”
