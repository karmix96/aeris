AERIS Aero Tests Report
Updated after AVL control-input fix
Date: 2026-03-26

Scope of this update
--------------------
This update fixes a real AVL control-surface bug in the AeroSandbox AVL solver path.

Previous behavior
-----------------
The AVL backend always sent a fixed control command equivalent to:
    d1 d1 1
for any geometry that contained control surfaces.

That meant:
- control-enabled geometry at zero deflection
- control-enabled geometry at +5 deg deflection

could collapse to the same AVL run, depending on how AeroSandbox exported CONTROL blocks.

Standalone forensic study findings
----------------------------------
A dedicated AVL equivalence study established the following:

1) When relying on AeroSandbox-exported control definitions alone,
   cs_zero and cs_plus5 produced identical results.
   Root cause: the exported .avl files did not encode actual commanded
   control magnitude in a way that changed the run.

2) Switching to explicit AVL OPER control commands fixed the issue.
   Commanded control value is now sent explicitly through:
       d1
       d1
       <value>

3) With explicit OPER control input:
   - no_cs and cs_zero became equivalent in the standalone study
   - cs_plus5 produced clear aerodynamic changes relative to cs_zero

Key solver changes
------------------
1) Added detection of whether the airplane contains any control surfaces.
2) Added explicit solver option:
       control_input_deg
3) Replaced fixed implicit control command with explicit AVL OPER command:
       d1 / d1 / <value>
4) Propagated control_input_deg through:
       CLI -> pipeline -> AeroSolverSettings.solver_options -> AVL backend
5) Persisted commanded control value into solver metadata and manifests.

Interpretation of current confidence
------------------------------------
What is now strongly verified:
- explicit control input is passed correctly through AERIS plumbing
- AVL keystrokes change according to commanded control_input_deg
- metadata/manifests record the commanded value
- a real standalone AVL study showed aerodynamic differences between 0 and +5 deg

What is not yet fully guaranteed:
- that every future geometry export contains correctly placed control surfaces
- that every control-enabled geometry family behaves identically
- that commanded +5.0 maps to an exactly validated physical flap/elevon rotation of +5.0 deg in all conventions
- that sign convention / trailing-edge direction is documented and locked for all cases
- that large dataset runs with control-enabled geometries are robust across all samples

Recommended next validation step
--------------------------------
Run a real AERIS dataset/campaign using control-enabled geometry and compare:
- control_input_deg = 0.0
- control_input_deg = +5.0
across a small but real case set.

That is the next meaningful systems-level validation.
